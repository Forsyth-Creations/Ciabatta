The modern monorepo is plagued by a number of issues:

- Packages published somewhere that someone needs 
- Unknown scripts that can be run in the monorepo that no one really maintains/knows what they do
- Redundant scripts that basically do the same thing, but are implemented in different ways across different packages
- Lack of clear ownership of packages and scripts, leading to confusion about who is responsible for maintaining them
- Missing necessary build toolchains, and not knowing how to resolve them
- Scripts that are "dependant" on other scripts, but the dependencies are not clearly defined or documented

Here's what we're going to do. Ciabatta will be the monorepo orchestration tool. The follow is as follows:

- Any sub-workspace that wants to opt in can run a 'ciabatta init --lib'. This will create a .ciabatta folder, which will contain, in itself, a ciabatta.toml to describe the sub-workspace, and workflow files to describe the scripts that can be run in the sub-workspace. The ciabatta.toml will also contain a list of dependencies on other sub-workspaces, which will be used to determine the order in which scripts are run. Let's say you run a "build". Ciabatta will go look at every "build" flow, and create one large graph to illustrate the order in which scripts should be run, based on the dependencies defined in the ciabatta.toml files. This will ensure that all necessary scripts are run in the correct order, and that any missing dependencies are flagged for resolution. This is what will be rendered to the user when they run a "ciabatta build" command. The user will be able to see the entire graph of scripts and their dependencies, and can choose to run the entire build or just specific parts of it.
- Let's say I have a build script in sub-workspace A that is dependent on a proto file generated by sub-workspace B. In the ciabatta.toml for sub-workspace A, I would specify that it depends on sub-workspace B's "proto" script. When I run "ciabatta build" in sub-workspace A, Ciabatta will first check if sub-workspace B's "proto" script has been run. If it hasn't, Ciabatta will automatically run it before proceeding with sub-workspace A's build script. This ensures that all dependencies are resolved and that the build process is smooth and error-free. All of these will be visible on one cohesive graph for the user, so they know exactly what is happening. The user can also specify --dry-run to see what would happen without actually executing the scripts, which is useful for debugging and understanding the flow of the build process.
- When running a script, the user can also specify a --env, which will allow them to set environment variables that will be passed to the scripts being run. This is useful for customizing the behavior of scripts based on different environments, such as development, staging, or production. The environment variables can be defined in a .env file in the sub-workspace, and Ciabatta will automatically load them when running scripts. This ensures that scripts have access to the necessary configuration and settings without requiring manual intervention from the user. This also allows the whole workspace, if it so chooses, to adopt a standard set of environment variables that can be used across all sub-workspaces, ensuring consistency and reducing the risk of misconfiguration.
- Each build script can have a description of exactly what it does, and what it requires.
- I should be able to see exactly what scripts are available across my whole workspace, and what they do, without having to dig through each sub-workspace to find them. Ciabatta will provide a command to list all available scripts, along with their descriptions and dependencies. This will make it easy for users to discover and understand the available scripts, and to determine which ones they need to run for their specific use case. Additionally, Ciabatta will provide a search functionality that allows users to quickly find scripts based on keywords or tags, further improving the discoverability of scripts within the monorepo. This can be done in the GUI
- When you init a sub workspace, or make a "run" file, you should be encouraged to add a description and your name, so that there is ownership and accountability for the script being created
- When the graph is shown, it should be clear which node came from which sub-workspace
- The "push" command should also be able to have the same dependencies. In fact, make the "push" just a special step option in a "run" command, kind of like how in Github you have a "setup AWS" phase. "push" is just a special, identifiable step
- It should be noted that some steps could be persistent. In this case, their nodes would hang and make for graphs that hang or get stuck. In this case, the user should be able to specify a "timeout" for a step, and if it exceeds that time, it will be marked as failed and the graph will continue to run. This ensures that long-running or potentially hanging steps do not block the entire build process, allowing for more efficient and reliable builds. Additionally, Ciabatta will provide options for retrying failed steps, allowing users to easily recover from transient errors without having to manually intervene in the build process. Users can allow a job to be persistent, and click a button to begin tailing it's logs through a `ciabatta watch`.
