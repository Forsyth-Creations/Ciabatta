# 0.3.0 — One pattern: everything is a workflow

Recipes and cookbooks go away. Publishing and fetching artifacts stop being a
separate schema with its own four-stage pipeline and its own CLI verbs, and
become what everything else in a monorepo already is: a step on a workflow
graph.

## Why

Ciabatta grew two ways to describe work, and a new user had to learn both before
they could do anything:

- **Recipes** (`recipies:` in `.ciabatta/ciabatta.yaml`) — a named artifact plus
  how to ship it, run through a fixed `login → pre → main → post` pipeline in
  one of three directions (`push`, `pull`, `run`). Single-project. Grouped into
  **menus**, selected with `--cookbook`.
- **Workflows** (`.ciabatta/workflows/<name>.yaml`) — a named DAG of steps that
  spans the monorepo, following `needs` and `depends_on` across packages.

The two already collapse into one at run time: `install_as_recipe` folds a
compiled workflow graph into a synthetic recipe so it can reuse the run engine,
and its own comment admits the truth — *"Downstream, a workflow is a run."* The
only thing the recipe schema still buys is the built-in registry transfer, and
that is one step's worth of behaviour, not a second way to describe a project.

Meanwhile the seam leaks. A workflow step already reaches back across it with
`kind: push` + `recipe: <name>`, which shells out to `ciabatta push` in its own
sub-workspace — a graph node whose real work is described in a different file,
in a different schema, with a different execution model, and which is invisible
to the dependency graph, the cache, and the environment report.

0.3.0 deletes the second pattern instead of maintaining the bridge.

## The shape

A step gains the transfer fields directly. `kind: push` and `kind: pull` select
the built-in registry action; every other step is unchanged.

```yaml
# packages/api/.ciabatta/workflows/release.yaml
description: Build and publish the API binary
needs: [proto:generate]

steps:
  - name: build
    run: cargo build --release
    requires: [cargo]

  - name: publish
    kind: push
    needs: [build]
    registry: nexus
    artifact: target/release/api.tar.gz
    publish_path: api/{CIABATTA_PATH}/api.tar.gz
```

Pull is the same artifact, the other way. Rather than restate it, a `pull` step
names the push step it mirrors — `<workflow>:<step>`, or a bare `<step>` for one
in the same workflow:

```yaml
# packages/api/.ciabatta/workflows/fetch.yaml
steps:
  - name: fetch
    kind: pull
    from: release:publish
```

`from` copies `registry`, `artifact`, `local_image`, `publish_path` and
`strip_prefix` from the named step; anything the pull step sets itself wins over
what it inherits. A pull step may also spell all of it out and skip `from`.

### What each recipe field becomes

| Recipe field | Step field | Notes |
|---|---|---|
| `registry` | `registry` | unchanged |
| `local_artifact_path` | `artifact` | renamed; "local" and "path" were both implied |
| `local_image` | `local_image` | unchanged |
| `publish_path` | `publish_path` | unchanged, both the single and glob-list forms |
| `strip_prefix` | `strip_prefix` | unchanged |
| `login` | *(registry's `login_script`)* | per-recipe login override goes; a registry logs in once per run |
| `pre` / `post` | *(a `needs` edge)* | a step before or after it on the graph, which is what they always were |
| `main` / `bash_script` | `run` / `script` | a step with its own command is just a step |
| `[recipies.x.run]` | the workflow file | `flowchart:` / `entry:` indirection goes; the workflow file *is* the DAG |
| `menus:` + `--cookbook` | `--filter` | `ciabatta release --filter tag:frontend` |

### CLI

`ciabatta push`, `ciabatta pull` and `ciabatta run` are removed. Publishing is a
workflow, so it is invoked the way every workflow is:

```
ciabatta release                    # every `release` workflow, in dependency order
ciabatta release --only api         # start from one package
ciabatta release --filter kind:push # just the publishing steps
ciabatta release --graph            # draw it, run nothing
```

`ciabatta list` drops its recipe section. `ciabatta configure` and
`ciabatta convert` emit workflow steps instead of recipe entries.

### Removed outright

`recipies:` and `menus:` are gone from the schema with no converter. A config
that still declares either is refused at load with a message naming the step
fields to write instead. Registries are untouched — `registries:` keeps working
exactly as it does today, and is now what a `kind: push` step points at.

## Work

1. **Schema.** Delete `RecipeEntry`, `SimpleRecipe`, `CiabattaConfig::recipes`,
   `CiabattaConfig::menus` and `resolve_recipes` from `src/config.rs`. Keep
   `PublishPath`, `RegistryConfig` and `validate_publish_path` — they now serve
   steps. Reject a config carrying `recipies:` or `menus:` with a message that
   names the replacement.
2. **Step.** Add `registry`, `artifact`, `local_image`, `publish_path`,
   `strip_prefix` and `from` to `RunStep`. Resolve `from` when the graph is
   compiled, so a step is self-contained by the time anything executes it.
   `RunStep::recipe` goes.
3. **Graph.** Replace `install_as_recipe` with a direct
   `WorkflowGraph → ResolvedRun` conversion. Nothing synthesises a recipe any
   more.
4. **Engine.** Teach `src/run/engine.rs` the push and pull actions, calling the
   transfer primitives directly. A transfer step reports progress, caches and
   appears in the dependency graph like any other node.
5. **Runner.** Reduce `src/runner.rs` to those primitives — login, transfer
   building, pull commit resolution — and delete the stage pipeline, `RunMode`,
   `validate_recipes` and `execute_recipe`.
6. **CLI.** Remove `Push`, `Pull`, `Run` and `--cookbook` from `src/cli.rs` and
   their handlers from `src/main.rs`.
7. **UI.** Rename recipe to workflow through `src/tui/`, `src/run/view.rs` and
   the daemon routes, so the run view says what it is showing.
8. **Generators.** `configure.rs`, `configure auto` and `convert.rs` write
   workflow steps.
9. **Docs.** `CONFIG_HELP` (`ciabatta config reference`), `README.md`,
   `MONOREPO.md`, the in-app manual (`tool_frontend/src/pages/DocsPage.tsx`) and
   the public site (`frontend/src/main.js`).

## Not in scope

Caching, the remote cache, `analyze`, `watch`, `todo` and the AI assistant are
untouched beyond the renames that follow from the above. A transfer step becomes
cacheable *because* it is now a normal step, but no new cache behaviour is
designed here.
