We're going to make Ciabatta a true Monorepo manager, complete with the following features:
- Anyone should be able to spin up a remote cache using the command "ciabatta remote-cache init" and "ciabatta remote-cache start" to start the cache server
- Users can authenticate to the remote cache server using "ciabatta remote-cache login" and "ciabatta remote-cache logout"
- A "project" is known to the remote cache server by its name and a unique identifier. The unique identifier is generated by the remote cache server when a project is first registered with the server. The unique identifier is stored in the workspace config for that project, and is used to identify the project when interacting with the remote cache server
- The remote cache can be configured to use LDAPS for authentication and authorization
- The remote cache should have it's own backend storage, which uses its own local file system
- For workspaces, cachcing is off by default. It's something users can opt into, it is not a system default
- There should be a helper command to get you started configuring a workspace. In the workspace config, you should have an array of file-selector pattern to specify the source files. If these files change, expect a rebuild. If they don't change, expect a cache hit.
- Let me do a dry-run of a reipie to see what would be a cache hit and what would be a rebuild. This should be done with the command "ciabatta dry-run <recipe-name>"
- Also specify what files are expected to be generated by the recipe. If these files are not generated, expect a rebuild. If they are generated, expect a cache hit. Keep track of the SHA256 of the generated files to determine if they have changed since the last build.
- If the daemon is running a remote cache, add a page to the website to show the status of the remote cache server, including the number of cache hits and misses, and the current storage usage. The remote cache should also keep track of how old cached artifacts are, and automatically clean up old artifacts to free up space. Users should be able to configure the retention policy for cached artifacts.


Other bug fixes and improvements:
- All config files should use "yaml" instaed of "toml" for better readability and maintainability
- The "todo" page on the website should be project-specific, and should rely on the project selector at the top of the page to determine which project to show todos for
- I should be able to remove projects from the project selector
- I should be able to edit todo items in-line
- "Recipies" are just "scripts". Make me a CLI command called "ciabatta convert --script <path-to-script>" that will convert a script into a recipe. The recipe should be generated in the .ciabatta directory for that workspace
- Ciabatta should always default to the .env file. However, users can tell ciabatta to use a different env file by specifying the path to the env file in the workspace config. This will overwrite the .env file for that workspace
- If you expect to use environment variables, the .env.default should be required to be specified in the workspace config. This will be used to generate the .env file for that workspace. If the .env.default file is not specified, ciabatta should throw an error when trying to build a recipe that expects environment variables
- `watch` should always use whatever the active environment variables are, and should always tell you/print them to the terminal


More additions:
- The remote cache has a version assigned to it. In the config file for the remote cache, I can specify the path to the windows and linux binaries for ciabatta. If these files ever get updates, the remote cache can let the users connected to the remote cache to know that there is a new version of ciabatta available, and they can download the new version from the remote cache server. When this happens, they should be able to run a `ciabatta self update` command to update their local ciabatta binary to the latest version. The remote cache should also keep track of the SHA256 of the binaries, and if the binaries change, it should notify the users connected to the remote cache that there is a new version available.
